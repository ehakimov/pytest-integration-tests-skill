# pytest-integration-tests

[English version](README.md)

Два [Agent Skills](https://agentskills.io), с которыми Claude пишет интеграционные автотесты на Python так, как их пишет опытный QA-автоматизатор: по слоям, с отчётом Allure, который объясняет падение без чтения кода, и с фикстурами, безопасными для параллельного запуска. В комплекте — рабочий пример проекта, собранный прямо из скиллов и проверяемый в CI.

Тексты скиллов и код ядра — на английском. Шаги, заголовки и сообщения в тестах агент пишет на языке проекта; категории отчёта от языка не зависят.

## Зачем

Без правил агент пишет тесты «как получится»: `requests` прямо в тесте, `time.sleep` вместо ожиданий, `assert r.status_code == 200` без контекста, токен на всю сессию без обновления. Такие тесты трудно читать, они флакают в параллельном прогоне, а отчёт не отвечает на вопрос «что сломалось».

Скиллы описывают архитектуру, на которой держится большой рабочий набор интеграционных тестов: несколько сервисов, API, UI и события Kafka, прогон по расписанию в CI с Allure TestOps. Всё специфичное для одной компании из неё убрано:

- тест читается как бизнес-сценарий: данные → шаги → проверки;
- отчёт Allure показывает шаги, запросы и ответы, историю ожиданий и категорию падения;
- тесты независимы и идут в N потоков на любом стенде;
- инфраструктура живёт в одном месте и одинакова во всех проектах.

## Что внутри

| Скилл | Когда срабатывает | Что даёт агенту |
| --- | --- | --- |
| [`pytest-integration-tests`](skills/pytest-integration-tests/SKILL.md) | «напиши автотест», «покрой тестами эндпоинт», прислан OpenAPI, упавший или флакающий тест, ревью тестов | слои и запреты, шаблоны теста, шагов, клиента, модели, проверок и фикстур, правила Allure и xdist, как работать в проекте с другим каркасом, разбор флаков, чек-лист; UI и Kafka — в `references/` |
| [`pytest-integration-bootstrap`](skills/pytest-integration-bootstrap/SKILL.md) | новый тестовый проект, новое место работы, починка таймаутов, токенов, отчёта или CI | ядро настоящими файлами в `templates/` и `scripts/scaffold.py`, решения и их причины, CI для GitLab и GitHub с опциональным TestOps, таблица типовых поломок |

Скиллов два, потому что ядро нужно редко: при создании проекта или починке инфраструктуры. Основной скилл подгружается при каждом тесте и не тащит с собой сотни строк инфраструктуры. Ядро агент не перепечатывает из Markdown — его копирует скрипт и никогда не перезаписывает существующие файлы.

## Установка

### Claude Code: плагином (рекомендуется)

```bash
claude plugin marketplace add OWNER/pytest-integration-tests
claude plugin install pytest-integration-tests@pytest-integration-tests
```

Внутри сессии: `/plugin marketplace add OWNER/pytest-integration-tests`, затем `/plugin install pytest-integration-tests@pytest-integration-tests`. Вызвать вручную: `/pytest-integration-tests:pytest-integration-tests` или `/pytest-integration-tests:pytest-integration-bootstrap`.

### Claude Code: без плагина

```bash
git clone https://github.com/OWNER/pytest-integration-tests.git
cp -r pytest-integration-tests/skills/* ~/.claude/skills/                       # для всех проектов
cp -r pytest-integration-tests/skills/* path/to/your-tests/.claude/skills/      # или для команды, в репозиторий
```

### Приложение Claude (claude.ai и desktop)

1. Скачай `pytest-integration-tests.zip` и `pytest-integration-bootstrap.zip` со страницы Releases или собери: `python tools/package_skills.py` (появятся в `dist/`).
2. Customize → Skills → «+» → Create skill → Upload a skill, загрузи оба архива.

Нужно включённое выполнение кода ([справка](https://support.claude.com/en/articles/12512180-use-skills-in-claude)).

## Как пользоваться

| Запрос | Что делает агент |
| --- | --- |
| «Покрой тестами POST /orders, вот swagger» | читает конвенции проекта и соседние тесты; добавляет метод клиента, шаги, проверки со схемой, позитивный и параметризованный негативный тест, маркер; запускает `--collect-only`, `ruff` и только новые тесты, если стенд доступен |
| «Подними каркас тестов для сервиса платежей: dev и stage, Keycloak, нужен UI» | спрашивает недостающее, запускает `scaffold.py`, заполняет `config.yml` и `.env.example`, пишет первый тест и проверяет отчёт |
| «Тесты через 10 минут падают с 401» | находит причину по таблице поломок и переносит `TokenAuth`, не ломая сигнатуры |
| «Тест флакает в CI» | идёт по процедуре: категория в отчёте, одиночный прогон, `-n 4`, повторы — и чинит причину в её слое |
| «Отревьюй tests/payments/» | проходит по чек-листу и правилам слоёв |

В существующем проекте его конвенции главнее скилла. Если в проекте свой HTTP-клиент, свои проверки или нет Allure, агент переносит правила на то, что есть, и не переделывает проект попутно.

## Отчёт

- шаги — бизнес-действия и «Checking …», у каждого HTTP-вызова два аттача, секреты замаскированы в любом стиле ключей, в form-телах, query и сообщениях проверок; в имени ответа — `X-Request-Id` для поиска логов;
- ожидание — один шаг с историей опроса и последним ответом;
- категории (первая подходящая выигрывает): **Environment unavailable** → **Timed out waiting for a state** → **Product defects** (failed) → **Test defects** (broken). Сопоставление идёт по классам исключений, а не по текстам;
- у упавшего UI-теста — скриншот и `trace.zip`.

## Ключевые решения

1. Тест не знает про HTTP: только шаги и `assert_*`.
2. Объект шагов = сущность теста, клиент — его поле; `try_create()` для проверяемого действия, `create()` для предусловия. Шаги не лезут в ответ по ключу, поэтому странный ответ продукта сообщает проверка, а не `KeyError`.
3. Проверки — в `asserts/`; `AssertionError` = дефект продукта, 502/503/504 — `EnvironmentUnavailable`.
4. Один HTTP-клиент: таймаут всегда; соединение повторяется для любого метода, 502/503/504 — только для GET/HEAD/OPTIONS; `Retry-After` игнорируется.
5. Авторизация профилями: OAuth2 (любой IdP), Basic, API-ключ или без неё; токен кэшируется по всей форме запроса.
6. Ожидания — один `wait_until`.
7. Данные — dataclass + `default_factory`, негатив — мутации валидного тела, даты сравниваются через нормализатор.
8. Параллельность — session-фикстура с `xdist_group`, которая убирает за собой; созданное тестом удаляет фикстура-реестр, в том числе в негативных тестах.
9. Стенд выбирается `--env` без значения по умолчанию; секреты — `.env` и переменные CI.
10. UI — свои фикстуры вместо pytest-playwright, браузер из конфига.
11. Kafka — слушатель с текущего конца партиций, сразу падает на несуществующем топике, не умирает на бинарных сообщениях; отправка ждёт подтверждения брокера.

## Пример и проверка репозитория

`example/` собирается из скиллов (`python tools/build_example.py`, сверка — `--check`) и запускается на демо-стенде — см. [example/README.md](example/README.md). `python tools/verify.py` проверяет пример, ruff, тесты в три потока, отчёт, отсутствие демо-секретов в `allure-results`, ретраи GET и то, что POST не повторяется, а нарочные падения попадают в свои категории. В CI ещё прогоняются проект из `scaffold.py` без UI и Kafka, слушатель Kafka на настоящем брокере и `claude plugin validate`; релиз по тегу запускает те же проверки и сверяет тег с версией плагина.

## Развитие

1. Правь скиллы: правила — в `SKILL.md`, ядро — в `templates/`, доменные шаблоны — в блоках кода основного скилла.
2. `python tools/build_example.py`, затем `python tools/verify.py`.
3. Pull request. Для выпуска подними `version` в `.claude-plugin/plugin.json`, допиши `CHANGELOG.md` и поставь тег `vX.Y.Z`.
